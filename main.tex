\begin{abstract}
Mapping natural-language requests to executable tool workflows (which we call \emph{intent mapping}) is a bottleneck in agentic systems. Two brittleness modes recur: semantic drift during single-tool selection and edge hallucination during multi-step planning. We address each with a decoupled retriever. For single-tool selection, we pair a zero-shot LLM router with a \emph{Functional Categorization} that groups tools by action type rather than topic. For multi-step planning, we introduce \textbf{Latent Execution-Graph Retrieval (LEGR)}, a dual encoder that retrieves a pre-validated execution DAG. The current V3 architecture shares one MiniLM backbone between requests and tool-name nodes and fuses an attention-pooled node-set representation with a directed GNN representation. We evaluate on Campaign V4, which contains 651, 916, and 1,313 unique DAGs at 15, 30, and 45 tools and reserves Diamond and Asymmetric Fork-Join families for topology-held-out testing. On the full 45-tool gallery, LEGR V3 reaches exact-DAG Recall@1 of 0.418 and Tool-Set F1 of 0.971, versus 0.255 and 0.978 for a standard single-model fine-tuned Sentence-BERT baseline. Its synchronized batch-one online latency is 5.39\,ms after a one-time 212.3\,ms gallery-indexing step. A matched latent-space analysis and frozen atomic-routing transfer test provide mixed rather than uniformly positive evidence for action-oriented organization, so we retain Functional Categorization and LEGR as complementary components. Code and data: \href{https://github.com/tanay-kadam/LEGR}{LEGR}.
\end{abstract}

\section{Introduction}

Tool-augmented LLMs rely on \emph{intent mapping} to translate user requests into appropriate tools and valid \emph{execution structures} (e.g., directed acyclic graphs, DAGs) that respect data dependencies \cite{mialon2023augmented,shen2023hugginggpt,song2023restgpt}. This translation must be precise: selecting a tool with an incorrect action type (e.g., a write instead of a read) can create unintended side effects, and inaccurate edges can corrupt downstream inputs.

Agentic systems struggle with intent mapping in two ways. \textbf{(1) Semantic drift in single-tool selection.} Tools are commonly exposed under human-friendly topic categorizations (e.g., HR, Finance) or domain-specific semantic splits (e.g., chemistry/biology \cite{ding2025scitoolagent}). Topic labels are unreliable proxies for a tool's function when sibling tools share nouns but differ in side effects, so tool retrievers overfit to topical keywords and become brittle under paraphrasing or lexical variation. \textbf{(2) Edge hallucination in multi-step planning.} For multi-step tasks, even recent graph-augmented planners \cite{chen2026gtool,xiu2026optgraph} let an LLM serialize plans token by token, so latency scales linearly with plan size and validation-guided repair cycles are often needed to fix hallucinated dependency edges.

We address these two sub-problems with two decoupled retrievers dispatched by a task-complexity gate (see \S\ref{sec:overview}): atomic single-tool requests are handled by a training-free single-tool retriever built on Functional Categorization; multi-step requests are handled by LEGR. We deliberately decouple the paths because a wrong atomic-selection decision propagates as a silent structural error through every downstream edge of a compounded plan; the tradeoff is that the two paths do not share evidence at inference, which we revisit in \S6. Our contributions are:
\begin{itemize}
    \item We propose a training-free \textbf{single-tool retriever} built on a \textbf{Functional Categorization} (tools grouped by action type rather than domain topic), which mitigates semantic drift and improves routing accuracy by up to 18.5 percentage points under lexical variation at the 15-tool scale.
    \item We introduce \textbf{Latent Execution-Graph Retrieval (LEGR)} for multi-step planning, formulating orchestration as retrieval over a pre-indexed DAG corpus rather than autoregressive plan synthesis.
    \item We develop LEGR V3, which shares one MiniLM backbone across the query and tool-name paths and fuses set-attention and directed message-passing representations; we compare it with the separate-node-encoder V2 architecture as an ablation.
    \item We evaluate an optional Graph Edit Distance (GED) auxiliary objective and show that its effect is scale- and architecture-dependent rather than uniformly beneficial.
    \item We measure synchronized indexing and online latency for every V2/V3 and GED/no-GED variant, audit whether V3's latent geometry transfers to atomic routing without fine-tuning, and show that a residual routing adapter over frozen V3 embeddings substantially improves atomic accuracy without modifying the original checkpoint.
    \item We release Campaign V4, a three-scale benchmark with 22 topology families, structural-twin candidates, and leakage-controlled held-out evaluation on Diamond and Asymmetric Fork-Join workflows.
\end{itemize}

\section{Background and Related Work}

\textbf{Single-tool selection and semantic drift.} Tool-augmented LLMs can emit syntactically valid tool invocations \cite{schick2023toolformer,patil2023gorilla} and are evaluated by benchmarks such as ToolBench \cite{qin2023toolllm} and BFCL \cite{yan2024berkeley}, with agent frameworks such as AutoGen \cite{wu2023autogen} formalizing agent--tool interactions. In deployment, tools are typically exposed through \emph{topic categorizations} (e.g., HR, Finance) or domain-specific semantic splits (e.g., SciToolAgent's chemistry/biology categorization \cite{ding2025scitoolagent}). Such labels do not always separate operationally distinct actions (e.g., a read vs.\ a write) that share nouns, leaving routers vulnerable to lexical shifts and ``confusable siblings.'' We instead group tools by \emph{action class} (read, write, orchestrate) and use this Functional Categorization inside a zero-shot LLM router, aligning the routing boundary with system-side risk rather than domain topic.

\textbf{Generative and graph-augmented planning.} Multi-step tool use requires producing an \emph{execution structure} that captures dependencies. The dominant approach serializes a workflow textually and lets an LLM emit it token by token (e.g., ReAct \cite{yao2022react}, DSPy \cite{khattab2023dspy}). Recent graph-augmented frameworks such as GTool \cite{chen2026gtool}, OptGraph \cite{xiu2026optgraph}, and TGR \cite{gao2025tool} narrow the modality gap by feeding graph tokens or validation feedback back into the LLM, but they remain autoregressive: decoding $N$ tokens takes $N$ sequential passes, scaling latency as $\mathcal{O}(N)$, and typically still requires validation-guided repair loops to fix edge hallucinations. GTool trains a missing-dependency predictor (MDPL) and TGR uses a gatekeeping discriminator, but both keep the plan itself in the token stream.

\textbf{Retrieval for tool use.} Retrieve-then-generate pipelines fetch candidate APIs with sparse (BM25 \cite{robertson2009probabilistic}) or dense (Sentence-BERT \cite{reimers-gurevych-2019-sentence}) retrievers, then hand the shortlist to a generator. These retrievers treat candidates as flat text and therefore ignore the dependency structure that distinguishes ``the same tools chained'' from ``the same tools fanned out.'' Knowledge-Graph embedding methods (TransE, DistMult) are also not a fit for our setting: they are transductive, score triples inside a single fixed graph, lack a natural-language text encoder, and embed individual nodes rather than whole candidate DAGs. Aligning natural-language intents with executable DAGs directly in a shared latent space remains, to our knowledge, underexplored. LEGR maps queries and DAGs into a shared space natively and evaluates an optional Graph Edit Distance (GED) auxiliary objective \cite{sanfeliu1983distance} intended to emphasize topology-sensitive errors.

\section{Methodology}

We formalize intent mapping into two decoupled retrieval tasks: (1) a training-free \emph{single-tool retrieval} step via a \emph{Functional Categorization}, and (2) a dual-encoder model, \textit{Latent Execution-Graph Retrieval} (LEGR), for \emph{multi-step planning} that predicts how tools are composed into an execution DAG.

\subsection{Formalizing Intent Mapping}
\label{sec:overview}
Let $q$ be a user request. Let $\mathcal{T}$ denote the tool library, and let $\mathcal{C} = \{\mathcal{G}_1,\dots,\mathcal{G}_{|\mathcal{C}|}\}$ be a corpus of \emph{candidate execution DAGs} curated offline. Each DAG $\mathcal{G}=(\mathcal{V},\mathcal{E})$ represents a valid multi-tool workflow, where nodes are tool invocations and edges encode data or control dependencies. The goal is to output a workflow $\hat{\mathcal{G}}$ that (i) calls the correct tools and (ii) matches the intended dependency structure.

A recurring source of brittleness in prior systems is that they entangle two distinct design choices:
(i) \textbf{single-tool categorization}: the label space used to organize tools (i.e., the \emph{categorization}); and
(ii) \textbf{workflow planning}: the mechanism that constructs a multi-step execution structure (e.g., a tool chain vs. a fan-out DAG).
We address these separately. First, we define a categorization that better matches tool \emph{action types}. Second, we plan by retrieving an execution DAG.

\paragraph{Framework overview.} Our two solutions are complementary rather than composed. A deployed system uses a lightweight upstream classifier to decide whether an incoming request is \emph{atomic} (a single tool call) or \emph{compositional} (a multi-step workflow), and dispatches it to the single-tool retriever (\S\ref{sec:fc}) or LEGR (\S\ref{sec:legr}) respectively. We treat this task-complexity gate as an interface between the two sub-problems and do not evaluate the gate itself in this work; in practice a keyword heuristic or a short-prompt LLM classifier suffices. Robust handling of the gate's error surface, and the more ambitious step of a fully unified formulation (a single retriever indexing both atomic tools and multi-tool DAGs in one latent space, which would remove the gate entirely) are natural next steps we leave to future work.

\subsection{Sub-Problem 1: Single-Tool Retrieval via Functional Categorization}
\label{sec:fc}
Our single-tool retriever is a two-stage zero-shot LLM router: given a query, it first predicts a top-level category, then predicts the tool within that category. The variable we study is the \textbf{categorization} itself, i.e., the partitioning of the tool library into categories used for routing. We contrast two choices.

\textit{Topic-based Categorization} ($\mathcal{T}_s$) groups tools by topical or organizational subject (e.g., HR, Finance, IT). This can collapse operationally different actions into the same branch: \texttt{reset\_user\_password} (a credential \emph{write}) and \texttt{generate\_access\_report} (a read-only \emph{audit}) both fall under ``Identity Management.'' An LLM router keyed on $\mathcal{T}_s$ can then overfit to topic nouns (``access'', ``identity'') and become brittle under paraphrase, noun omission, or confusable wording.

We instead use a \textit{Functional Categorization} ($\mathcal{T}_f$), which groups tools by \textbf{action type} (the kind of external effect the tool can produce) so the categorization structure reflects the operational decision boundary. Concretely, we use three top-level action classes:
\begin{itemize}
    \item \textbf{State Modification:} state-changing tools (e.g., POST/PATCH requests, credential resets, record updates).
    \item \textbf{Data Retrieval:} idempotent, read-only tools (e.g., GET requests, audit queries, status checks).
    \item \textbf{Orchestration:} meta-tools that manage control flow (e.g., conditional branching, delegation).
\end{itemize}
Structuring the categorization under $\mathcal{T}_f$ reduces reliance on brittle topic vocabulary by emphasizing what the tool \emph{does} (read vs. write vs. control), not what the request \emph{talks about}. Functional Categorization is a scheme, not a model: combined with the two-stage LLM router above, it forms a training-free single-tool retriever. Our comparison in \S\ref{sec:results-fc} runs the identical router over $\mathcal{T}_s$ and $\mathcal{T}_f$, so the label space is the only variable.

\subsection{Sub-Problem 2: Latent Execution-Graph Retrieval (LEGR)}
\label{sec:legr}
LEGR replaces autoregressive plan synthesis with \emph{bi-encoder retrieval} in a shared latent space $\mathbb{R}^d$. We use the V3 encoder in the main experiments and retain V2 only for the architectural ablation in Appendix~\ref{sec:architecture-ablation}.

\textbf{Shared text encoder.} A Transformer encoder $f_\theta(\cdot)$ (\texttt{all-MiniLM-L6-v2}) maps the request $q$ to an embedding $\mathbf{z}_q \in \mathbb{R}^d$. The same backbone also encodes readable tool names into node features; V3 therefore contains one MiniLM model, not independent query and tool-name models.

\textbf{Graph representation.} Each node $v\in\mathcal{V}$ corresponds to a tool invocation. The shared backbone encodes the tool name, a learned projection maps it to a 64-dimensional node feature, and a learned topological-position embedding supplies order information. Edges $\mathcal{E}$ are directed dependencies.

\textbf{Directed and set branches.} V3 uses two complementary graph summaries. A $k$-layer directed GNN applies separate transformations to predecessor and successor messages:
\begin{equation}
h_v^{(l+1)} = \sigma \left( \text{LN} \left( W_{\text{self}}^{(l)} h_v^{(l)} + \sum_{u \in \mathcal{N}_{\text{in}}(v)} W_{\text{in}}^{(l)} h_u^{(l)} + \sum_{w \in \mathcal{N}_{\text{out}}(v)} W_{\text{out}}^{(l)} h_w^{(l)} \right) \right)
\end{equation}
where $\mathcal{N}_{\text{in}}(v)$ and $\mathcal{N}_{\text{out}}(v)$ are the predecessor and successor nodes, $\text{LN}$ is LayerNorm, and $\sigma$ is ReLU. Mean pooling after $k=3$ layers gives a structural summary $\mathbf{z}_{\mathrm{gnn}}$. In parallel, a learned scalar attention score $a_v$ pools the pre-message-passing tool-name features into a permutation-invariant set summary,
\begin{equation}
\mathbf{z}_{\mathrm{set}}=\sum_{v\in\mathcal{V}}\frac{\exp(a_v)}{\sum_{u\in\mathcal{V}}\exp(a_u)}\mathbf{x}_v.
\end{equation}
The final DAG vector is $\mathbf{z}_g=\operatorname{Proj}([\mathbf{z}_{\mathrm{gnn}};\mathbf{z}_{\mathrm{set}}])\in\mathbb{R}^{256}$. The set branch preserves tool identity while the directed branch represents dependency flow.

\textbf{Inference (retrieval).} Text and graph embeddings are $\ell_2$-normalized ($\hat{\mathbf{z}} = \mathbf{z} / \|\mathbf{z}\|_2$) before comparison, so the dot product below is a cosine similarity. At test time, we retrieve the most compatible workflow from a pre-validated, pre-indexed corpus $\mathcal{C}$:
\begin{equation}
\hat{\mathcal{G}} = \arg\max_{\mathcal{G} \in \mathcal{C}} \; \hat{\mathbf{z}}_q^\top \hat{\mathbf{z}}_g.
\end{equation}
Because all candidate DAG embeddings can be pre-indexed, inference reduces to query encoding and nearest-neighbor lookup. Exact search is $\mathcal{O}(|\mathcal{C}|)$ and standard approximate indexing can reduce search complexity; unlike autoregressive synthesis, retrieval does not decode the output plan token by token.

\paragraph{Training objective.} LEGR is trained to align request and DAG embeddings with a symmetric contrastive objective. Given a batch of $B$ pairs $\{(q_i, \mathcal{G}_i)\}_{i=1}^B$, we form a similarity matrix $\mathbf{S}$ over $\ell_2$-normalized embeddings with entries $\mathbf{S}_{ij} = (\hat{\mathbf{z}}_{q_i} \cdot \hat{\mathbf{z}}_{g_j}) / \tau$, where $\tau$ is a temperature.

Standard InfoNCE treats all in-batch negatives uniformly. Because many Campaign V4 candidates share a tool multiset but differ in their edges, we also evaluate an optional Graph Edit Distance (GED) auxiliary term that emphasizes structurally close negatives.

Concretely, the total loss is:
\begin{equation}
\mathcal{L} = \frac{1}{2} \left( \text{CE}(\mathbf{S}, \mathbf{y}) + \text{CE}(\mathbf{S}^\top, \mathbf{y}) \right) + \lambda_{ged} \cdot \mathcal{L}_{ged}
\end{equation}
where $\text{CE}$ represents the standard cross-entropy loss over the similarity matrix. For reproducibility, the structural term below describes the evaluated implementation exactly:
\begin{equation}
\mathcal{L}_{ged}^{\mathrm{impl}} = \frac{1}{B} \sum_{i=1}^B -\log \frac{e^{\mathbf{S}_{ii}}}{e^{\mathbf{S}_{ii}} + \max\!\left(\epsilon,\sum_{j \neq i}\mathbf{S}_{ij}(1-w_{ij})\right)}
\end{equation}
where $w_{ij}$ is a normalized, margin-clamped GED between $\mathcal{G}_i$ and $\mathcal{G}_j$:
\begin{equation}
u_{ij}=\max\!\left(\frac{\mathrm{GED}(\mathcal{G}_i,\mathcal{G}_j)}{\mathrm{ged\_scale}}-\mathrm{margin},0\right), \qquad
w_{ij}=\frac{u_{ij}}{\mathrm{GED}_{\max}/\mathrm{ged\_scale}+\epsilon}.
\end{equation}
We pre-compute the pairwise GED matrix offline. The hyperparameters $\text{ged\_scale}$ and $\text{margin}$ control the penalty threshold: low-GED near misses retain more negative weight, whereas structurally distant graphs contribute less. Importantly, the implemented auxiliary denominator combines an exponentiated positive with weighted \emph{raw} negative logits, rather than exponentiating every logit as in a standard softmax. Consequently, this term is an implementation-specific ablation, not a normalized contrastive probability. Appendix~\ref{sec:architecture-ablation} reports both $\lambda_{ged}=0$ and $\lambda_{ged}>0$; on Campaign V4 it is not uniformly beneficial.



\section{Dataset and Experimental Setup}

We evaluate two questions: (i) whether \emph{Functional} categorization improves single-tool routing robustness under linguistic shift without training, and (ii) whether LEGR can retrieve the correct \emph{execution DAG} (including edges, not only tool sets) on unseen topology families. The execution-graph experiments use the new Campaign V4 benchmark.

\subsection{Benchmark Corpus and Held-Out Splits}
Campaign V4 uses a 45-tool master registry and nested 15-, 30-, and 45-tool subsets. We instantiate 22 programmatic DAG families over these tools and generate six natural-language requests per DAG with Azure GPT-4o. The generated requests are fixed before training. Structural-twin groups deliberately include graphs with the same tool multiset but different directed edges, preventing a tool-set-only encoder from solving the benchmark by construction.

Diamond and Asymmetric Fork-Join are excluded from training and development and appear only in \texttt{test\_topology\_heldout}. Canonical hashes over labeled nodes and directed edges enforce zero DAG overlap between the training/development and held-out partitions. Table~\ref{tab:dataset_v4} gives the audited counts; each DAG has six distinct requests. At evaluation, the gallery is the unique union of the candidate corpus and the evaluated test split, so every gold DAG is present exactly once.

\subsection{Linguistic Stress Conditions}
\label{sec:stress}
For categorization-routing experiments, we evaluate under four query conditions designed to isolate common routing failures:
\begin{enumerate}
    \item \textbf{Standard:} original queries with explicit intent.
    \item \textbf{Lexical:} keyword-masked or synonym-substituted queries to reduce noun matching.
    \item \textbf{Confusable:} queries targeting sibling tools with overlapping descriptions but different action types.
    \item \textbf{Paraphrase:} syntactic rephrasings with preserved intent.
\end{enumerate}

\subsection{Baselines and Metrics}
Because there is no established query-to-DAG retriever, our primary dense baseline is a standard single-model Sentence-BERT fine-tune. One \texttt{all-MiniLM-L6-v2} model encodes both requests and flattened DAG dependency strings and is optimized with Multiple Negatives Ranking Loss; it contains no second tower, custom projection, LEGR component, or GNN. We also report a frozen Sentence-BERT diagnostic at 15 tools. For generation, Llama 3.2 3B~\cite{meta2024llama32} and GPT-OSS 120B~\cite{openai2025gptoss} emit one JSON plan containing tools and directed edges. We do not benchmark contemporary graph-augmented planners directly because their input and training protocols do not map cleanly onto closed-corpus query-to-DAG retrieval.

For retrieval, exact-DAG accuracy equals Recall@1; we additionally report Recall@3, Recall@5, MRR@5, Tool-Set F1, and Mean Graph Edit Distance (GED, lower is better). Retrieval metrics use the complete held-out splits (300/420/600 requests). A generator emits no ranked list, so the LLM baselines instead report exact-match rate, Tool-Set F1, GED, validity, and latency on a fixed 50-request subset at each scale. We keep these protocols separate rather than relabeling generative Tool-Set F1 as Recall@1. For categorization routing, we report end-to-end accuracy under each stress condition in \S\ref{sec:stress}.

\subsection{Implementation Details}
\label{sec:impl}
LEGR V3 uses \texttt{all-MiniLM-L6-v2}~\cite{wang2020minilm,reimers-gurevych-2019-sentence}, 256-dimensional retrieval embeddings, 64-dimensional tool-name node features, a 3-layer directed GNN with hidden size 256, and the node-set attention branch described above. Sharing the text backbone yields 23.48M parameters. V2 instead uses a separate frozen MiniLM for node names and has 46.11M parameters.

\textbf{Training.} For LEGR, the bottom four of MiniLM's six transformer blocks are frozen; the top two blocks, embeddings, projection, set-attention branch, GNN, and temperature are trained. AdamW uses learning rates $2\times10^{-5}$ for the trainable backbone and $2\times10^{-4}$ for the remaining modules, weight decay $10^{-4}$, gradient clipping at 1.0, three warm-up epochs, batch size 128, maximum sequence length 128, and a 75-epoch cap with patience-15 early stopping. Temperature is learnable and initialized at 0.05. GED runs use $\text{ged\_scale}=2.5$, margin 0.05, and $\lambda_{ged}=0.10$ at 15 tools or 0.30 at 30/45 tools. The single-model Sentence-BERT baseline uses AdamW at $2\times10^{-5}$, batch size 128, a 100-epoch cap, and the same patience and sequence length. All models use seed 42.

\textbf{Hardware and latency protocol.} Model training and retrieval evaluation use one NVIDIA RTX 6000 Ada GPU. For each of the 12 V2/V3 checkpoints, we separately measure one-time gallery indexing and batch-one online retrieval. Online timing includes tokenization, host-to-device transfer, query encoding, exact cosine scoring against cached candidate vectors, and top-1 selection; it excludes model loading, file I/O, and graph indexing. We use 20 warm-up requests and three complete passes over each held-out query set, synchronizing CUDA around every measurement. Gallery indexing uses one warm-up and five timed repetitions with batch size 64. Llama runs locally through Ollama, whereas GPT-OSS 120B is cloud-served through Ollama; its latency includes network round-trip, so we report the protocols separately rather than claim a controlled hardware speedup.

\textbf{Evaluation counts.} The four linguistic stress conditions of \S\ref{sec:stress} contain 1005 Standard, 1005 Lexical, 450 Confusable, and 1255 Paraphrase queries at 15 tools. Campaign V4 topology-held-out retrieval contains 300, 420, and 600 requests over 50, 70, and 100 gold DAGs at 15, 30, and 45 tools. The corresponding full galleries contain 322, 455, and 650 unique DAGs.

For the LLM baselines, both categorization routing and query-to-DAG generation use default sampling with constrained JSON decoding; unparseable outputs and out-of-vocabulary selections are counted as failures. Both categorization schemes (Topic-based and Functional) use identical prompts, isolating the label space as the only independent variable.

\paragraph{Supervised routing adapter on frozen V3.}
To test whether atomic accuracy improves under realistic routing supervision without rewriting Campaign weights, we train a residual adapter on top of the frozen 15-tool V3 no-GED checkpoint. The adapter comprises a $256{\to}128{\to}256$ residual query MLP and 15 residual tool prototypes; MiniLM, set attention, directed GNN, and fusion weights receive no gradients, and the source checkpoint SHA256 is unchanged before and after training. The training corpus contains 900 independent routing utterances (60 per tool) and 150 held-out validation utterances, with zero exact normalized overlap against the four evaluation CSVs. \textbf{Branching-factor confound.} Functional Categorization uses three top-level branches (Data Retrieval, State Modification, Orchestration), whereas Topic-based Categorization inherits a finer-grained topical partition from the source benchmarks with $K>3$ branches. Part of the accuracy delta may therefore reflect the smaller branching factor rather than the label semantics alone. Two observations argue against a pure branching-factor artifact: (i) the gap widens under \textit{Lexical} and \textit{Confusable} conditions, where topical noun cues are precisely what is removed or disrupted, rather than staying flat as a pure coarseness effect would predict; and (ii) at 30- and 45-tool scales the three-way scheme itself becomes the limiting factor (see ``Categorization Granularity at Scale'' below), consistent with a coarseness--specificity trade-off rather than a monotonic ``fewer branches is better'' effect. We therefore scope the routing claim to the 15-tool, 3-vs-$K$-branch regime and note that hierarchical action categorizations are the principled way to disentangle the two factors.

\subsection{Matched Action-versus-Semantic Latent Geometry}
\label{sec:latent-geometry}

We probe whether frozen V3 graph embeddings organize more clearly by action type than by topic. The analysis uses all 322 unique DAGs in the 15-tool full gallery and one shared 256-dimensional embedding matrix. The action partition contains Data Retrieval, State Modification, and Orchestration. As a matched control, we construct three five-tool semantic groups (Account \& Subscription, Data \& Access Management, and Service \& Incident Operations), each containing exactly two retrieval, two modification, and one orchestration tool. Because a strict-majority rule produces no Orchestration-labelled DAGs in this gallery, we use a disclosed unique-plurality rule and label exact ties as Mixed; this yields four observed labels for each partition. Figure~\ref{fig:action-semantic-tsne} presents separate PCA and t-SNE views of each taxonomy after omitting Mixed cases for legibility. The action view contains 253 non-tied DAGs (131 retrieval, 116 modification, and 6 orchestration); the semantic view contains 196 (58 account/subscription, 51 data/access, and 87 service/incident). These separately fitted projections are descriptive and their axes are not directly comparable.

These results motivate a hybrid system: retrieval supplies a cheap shortlist and a stronger generator handles cases requiring synthesis or reranking.

\textbf{Categorization granularity at scale.} While LEGR scales for multi-step planning, the three-way Functional Categorization (read, write, orchestrate) used for single-tool routing becomes under-specified at 30 and 45 tools. Addressing this within-branch confusion calls for a hierarchical categorization, which we identify as future work.

\section{Conclusion}

We decoupled two brittleness modes in agentic intent mapping: semantic drift in atomic routing and structural ambiguity in multi-step planning. Functional Categorization improves zero-shot routing accuracy by up to 18.5 points under lexical stress. Frozen V3 atomic transfer is only moderate, but a residual routing adapter over the unchanged V3 no-GED checkpoint raises accuracy to 75.1\% / 48.7\% / 61.6\% / 73.5\% on Standard / Lexical / Confusable / Paraphrase. For multi-step tasks, LEGR V3 retrieves pre-validated DAGs using one shared MiniLM backbone, an attention-pooled tool-set branch, and a directed GNN branch. On Campaign V4, V3 without GED reaches exact-DAG Recall@1 of 0.418 at 45 tools, compared with 0.255 for the newly trained single-model Sentence-BERT baseline, while the baseline remains stronger at Recall@5. Online V3 retrieval takes 5.39\,ms at this scale after a one-time 212.3\,ms indexing step. V2 and GED/no-GED ablations show that both architecture and objective matter, whereas the matched geometry and frozen atomic-transfer analyses caution against claiming that action-oriented routing structure emerges automatically inside V3. The updated LLM results further show that GPT-OSS can achieve much higher exact generation accuracy on a 50-query subset, but at multi-second latency, motivating retrieval--generation hybrids rather than a blanket claim that one paradigm dominates.

\subsection*{Limitations and Future Work}
Several limitations bound our claims and point to natural next steps.
\textbf{(1) Retrieval is constrained by the pre-indexed corpus.} LEGR can only return workflows present in the offline candidate corpus $\mathcal{C}$; queries that require genuinely novel compositions are outside its scope. We do not measure the cost or coverage properties of curating $\mathcal{C}$, both of which will govern deployment feasibility.
\textbf{(2) The held-out topology evaluation remains controlled.} Campaign V4 expands coverage to 22 families, but structural generalization is tested on only Diamond and Asymmetric Fork-Join. Real workflows can contain cycles, conditional execution, and data-dependent control flow outside this benchmark.
\textbf{(3) Retrieval and generation solve different problems and use different evaluation sizes.} The candidate gallery contains the gold DAG for every retrieval query, whereas generators synthesize a graph. Retrieval uses all 300/420/600 held-out requests, while each LLM is evaluated on 50. Their values are informative but not a paired, equal-sized accuracy comparison.
\textbf{(4) Functional Categorization is coarse at scale.} The three-way scheme becomes under-specified at 30--45 tools (\S\ref{sec:results-scale}); a hierarchical action categorization is a natural remedy.
\textbf{(5) Cross-task transfer is limited without routing supervision.} Frozen V3 direct routing reaches only 27--29\% accuracy after lexical cue removal. A residual adapter over the frozen encoder improves this to 48.7\% Lexical and 75.1\% Standard accuracy without modifying the original checkpoint, but remains below the two-stage Functional routers and demonstrates supervised atomic adaptation rather than automatic transfer from multi-step graph retrieval. The Campaign V4 and routing tool names also differ, so the frozen baseline measures cross-dataset transfer rather than a controlled replacement for Functional Categorization.
\textbf{(6) Latent action structure is local rather than global.} The matched geometry audit finds higher action-neighborhood purity but lower action silhouette and 5-NN macro-F1 than the semantic control, with non-significant permutation tests. Larger balanced corpora are needed before drawing a general representation-level conclusion.
\textbf{(7) The evaluated GED auxiliary is implementation-specific.} Its denominator sums weighted raw negative logits alongside an exponentiated positive, so it is not a standard normalized contrastive probability. The reported GED/no-GED results characterize this code path only; a corrected exponentiated-negative formulation must be retrained before making a broader claim about GED-aware contrastive learning.
Hybridizing LEGR with a lightweight autoregressive fallback for novel workflows, extending the corpus to cover dynamic, data-dependent control flow, and directly benchmarking against graph-enhanced planners such as GTool and TGR are the primary directions for future work.
